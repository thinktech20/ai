# Query FSR — Tool Spec

**REST Tool:** `query_fsr`  
**Spec Owner:** DS team → **Impl Owner:** DEV team  
**Date:** 2026-03-05

---

## Summary

This document describes the target production behavior for a future `query_fsr` REST tool. The cleaned `fsr_pipeline_dbr_v6` package in this repo is still an experimental Databricks notebook workflow used to validate ingestion and retrieval quality; it does not yet implement this full service contract.

The Query FSR tool performs hybrid retrieval (semantic + keyword) over pre-chunked FSR (Field Service Report) documents whose embeddings are generated with a self-managed Azure OpenAI embedding model. Those embeddings are persisted in the Delta source table and indexed in Databricks Vector Search. At query time the tool accepts only the user query text, generates the matching `query_vector` internally with the same embedding model, and supplies both `query_text` and `query_vector` to Vector Search. It returns the top-k most relevant chunk records after reranking, enriched with structured metadata from three additional Databricks SQL views.

The standalone `query_fsr_with_metadata.py` implementation validated an important operational detail that this spec now makes explicit: the initial Vector Search call should return only the minimal chunk-identifying columns needed for ranking and traceability, and metadata enrichment should happen afterward only for the returned chunk IDs. The grouped response shape is therefore a second-stage assembly step, not a raw Vector Search response.

The tool is exposed as a **REST endpoint only** — no MCP endpoint is required. This reflects the current architecture decision to implement all tool interfaces as REST for the time being.

## Retrieval Validation Snapshot

Source: `docs/fsr_retrieval_metrics_final.csv`.

- 16 retrieval variants were compared across custom and Databricks-built-in approaches, with and without criteria text appended to the query.
- Best low-k Databricks-native result: **DBR built-in HYBRID + criteria** achieved **Recall@1 = 45.5**, **Recall@5 = 67.4**, and **Recall@10 = 78.8**.
- Best higher-k Databricks-native result: **DBR built-in Reranked + criteria** achieved **Recall@20 = 86.4**.
- Best overall experimental Recall@10: **Custom Hybrid_70_30 without criteria** reached **81.8**.
- Best overall experimental Recall@20: **Custom Hybrid_70_30 with criteria** reached **88.6**.
- Production implication: **Databricks native HYBRID + criteria** is the strongest low-latency baseline from this experiment, while reranking remains worth evaluating when deeper recall matters and additional latency is acceptable.

## Data Sources

### Primary: Vector Search Table (Chunks + Embeddings)

- **Production target table:** `vaid.ai_std_con_field_service_report.field_service_report`
- **Production target VS Index:** `vaid.ai_std_con_field_service_report.vs_field_service_report` (self-managed embedding index)
- **Current experiment default table/index:** `main.gp_services_sdg_poc.field_service_report` / `main.gp_services_sdg_poc.vs_field_service_report_gt_litellm`
- **VS Endpoint:** `pw-ser-sdg-vector-search`
- **Embedding model:** self-managed Azure OpenAI embedding deployment via LiteLLM (current runtime default: `azure-text-embedding-3-large-1`, 3072-dim)
- **Embedding persistence:** document embeddings are generated during ingestion, stored in the Delta table, and indexed in Vector Search; query embeddings are generated by the tool during retrieval

| Column | Type | Notes |
|--------|------|-------|
| `chunk_id` | STRING | PK — format: `{pdf_name}_{chunk_index}` or `{pdf_name}_{chunk_index}__{esn}` for multi-ESN chunks |
| `pdf_name` | STRING | Source PDF identifier (GUID) — **join key** to `fsr_pdf_ref` |
| `page_number` | INT | Chunk start page within the document, as stored by the current pipeline (not chunk ordinal) |
| `generator_serial` | STRING | ESN identified from report text via LLM + regex extraction (nullable). When a chunk is associated with multiple ESNs, the row is **duplicated** — one row per ESN — so that a VS equality filter on `generator_serial` surfaces the chunk for every tagged unit. |
| `report_date` | DATE | Report date extracted during ingestion (nullable) |
| `chunk_text` | STRING | The chunked text content (up to ~4 000 tokens) |
| `embedding` | ARRAY<FLOAT> | Self-managed Azure OpenAI embedding written during ingestion and indexed in Vector Search. This field is not returned to the caller. |
| `created_at` | TIMESTAMP | Row creation time |
| `uploaded_at` | TIMESTAMP | Row upload time |

### Supplementary: Structured Metadata Views (3 tables)

All three views are joined to the vector table results to enrich each returned chunk with structured FSR metadata.

| # | Alias | Full Table Name | Description |
|---|-------|-----------------|-------------|
| 1 | **FSR Report** | `vgpd.fsr_std_views.fsr_field_vision_field_services_report_psot` | Comprehensive field-services and business-unit details for outages — captures outage type, scope of work, site, emergency classification, equipment fired hours, start/end dates, and operational metrics. ~35,251 rows. |
| 2 | **PDF Ref** | `vgpd.fsr_std_views.fsr_pdf_ref` | Mapping of FSR documents in FieldVision to PDF files using FieldVision application metadata. Links report IDs to physical PDF filenames. |
| 3 | **Scraped Mapping** | `vgpd.fsr_std_views.fsr_scraped_file_mapping_ref` | Metadata extracted from Field Services Report PDFs via text scraping. Provides supplementary file-level metadata not available in FieldVision. |

### First-pass Vector Search return columns

The metadata-enrichment implementation only needs a small set of columns from the initial Vector Search query before it hydrates the full chunk row from the Delta table.

| Column | Purpose |
|--------|---------|
| `chunk_id` | Primary identifier used to reload the full chunk row from the chunk table |
| `pdf_name` | Filename join key for PDF metadata lookups |
| `page_number` | Page anchor when the full chunk row is unavailable |
| `chunk_text` | Retrieval text shown to callers and optionally reranked |
| `generator_serial` | ESN filter key and tie-break input for PDF metadata selection |

### Join Relationships

```
┌──────────────────────────────────────────────┐
│  field_service_report  (vector table)        │
│  pdf_name ──────────────── ① ────────────┐   │
└──────────────────────────────────────────────┘
                                            │
                                            ▼
               ┌──────────────────────────────────────────┐
               │  fsr_pdf_ref                             │
               │  filename  ◄──── ① (= pdf_name)         │
               │  filename  ──── ② ──────────────────┐    │
               │  (esn, event_id) ──── ③ ────────┐   │    │
               └──────────────────────────────────────────┘
                                                  │   │
                         ┌────────────────────────┘   │
                         ▼                            ▼
    ┌──────────────────────────────────┐  ┌─────────────────────────────────┐
    │  fsr_field_vision_...psot        │  │  fsr_scraped_file_mapping_ref   │
    │  (esn, event_id) ◄─── ③         │  │  filename ◄──── ②              │
    └──────────────────────────────────┘  └─────────────────────────────────┘
```

| Join | From | To | Key |
|------|------|----|-----|
| ① | `field_service_report.pdf_name` | `fsr_pdf_ref.filename` | PDF filename (GUID) |
| ② | `fsr_pdf_ref.filename` | `fsr_scraped_file_mapping_ref.filename` | PDF filename |
| ③ | `fsr_pdf_ref.(esn, event_id)` | `fsr_field_vision_...psot.(esn, event_id)` | Equipment serial + event |

> **Note on Join ③:** The `(event_id, esn)` composite key is not perfectly unique in the `_psot` table. Production implementation should explicitly deduplicate by preferring the row with the most advanced `report_unit_status` (Completed > Started > Not Started > Hold).

> **Filename normalization note:** the implementation had to normalize filename/path variants when joining (`guid`, `guid.pdf`, and path-qualified names). Production code should join on a normalized PDF stem, not on raw string equality alone.

> **PDF Ref selection note:** when multiple `fsr_pdf_ref` rows exist for the same PDF, prefer an exact `(pdf_name, esn)` match over filename-only matches before selecting the row used for downstream `_psot` enrichment.

## Inputs

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| `equipment_serial_number` | string | **Yes** | — | ESN to scope retrieval. Only chunks belonging to FSRs for this ESN are considered. |
| `query` | string | **Yes** | — | Natural-language search query (e.g., `"vibration issues during startup"`). Drives both semantic and keyword legs of hybrid retrieval. |
| `k` | integer | **Yes** | — | Number of top results to return. This is the final output size. |
| `query_type` | string | No | `HYBRID` | Retrieval mode. Current implementation supports `HYBRID` and `ANN`. Production may choose to keep this fixed to `HYBRID`. |

> The public API does not accept `query_vector`. Callers provide `query` text only; the service computes the vector internally with the configured Azure OpenAI embedding model.

### Input Validation

| Condition | Error |
|-----------|-------|
| `equipment_serial_number` is empty or missing | `400 Bad Request` — "equipment_serial_number is required" |
| `query` is empty or missing | `400 Bad Request` — "query is required" |
| `k` is missing or ≤ 0 | `400 Bad Request` — "k must be a positive integer" |
| `query_type` is provided but unsupported | `400 Bad Request` — "query_type must be one of: HYBRID, ANN" |

## Retrieval Pipeline

### Step 1 — ESN-scoped candidate set

Filter the vector table to only include records matching the provided `equipment_serial_number` (via equality filter on `generator_serial`).

### Step 2 — Generate query vector internally

Embed the provided `query` string with the configured self-managed Azure OpenAI embedding model. The caller does not provide `query_vector`; the service derives it at request time using the same embedding family used during ingestion.

### Step 3 — Vector Search retrieval (top `k`)

Execute a native Databricks Vector Search query against the self-managed VS index, passing both `query_text` and the internally generated `query_vector`.

For `HYBRID`, Databricks search combines:
- **Dense retrieval** — vector similarity against the supplied `query_vector`, generated from the Azure OpenAI embedding model
- **Learned keyword search** — BM25-style keyword matching against `chunk_text` using the original `query_text`

Results are fused internally via **Reciprocal Rank Fusion (RRF)** and returned with scores normalised 0–1.

The initial Vector Search request should return the minimal retrieval columns needed for downstream assembly:

- `chunk_id`
- `pdf_name`
- `page_number`
- `chunk_text`
- `generator_serial`

### Step 4 — Reranking (top `k`)

Apply the **Databricks built-in reranker** (`DatabricksReranker`, reranking on `chunk_text`) to the hybrid search results. Return the top `k` results.

### Step 5 — Chunk row hydration

Reload the full chunk-table rows for the returned `chunk_id` values before metadata enrichment. This allows the response to expose additional chunk columns such as `report_date`, `created_at`, and `uploaded_at` without overloading the initial Vector Search return set.

If a full chunk-table row cannot be found for a returned `chunk_id`, the service should still return a fallback `chunk` object assembled from the first-pass Vector Search row.

### Step 6 — Metadata enrichment

For each of the returned chunks, JOIN only those chunk rows to the three supplementary views (via the join relationships above) and include all columns from all four tables in the response.

The implementation showed that these follow-up lookups can be parallelized safely because they depend only on the returned `chunk_id` and `pdf_name` sets.

## Sample Query Code (Service Internal)

External callers to `query_fsr` submit only `equipment_serial_number`, `query`, and `k`. The service generates `query_vector` internally before calling Vector Search.

```python
import json
import requests

from your_service.vector_embeddings import get_query_vector

# Query details
equipment_serial_number = "270T658"
query_text = "What is the status of the equipment?"
k = 3
query_type = "HYBRID"

query_vector = get_query_vector(query_text)

response = requests.post(
  "https://<workspace-host>/api/2.0/vector-search/indexes/vaid.ai_std_con_field_service_report.vs_field_service_report/query",
  headers={
    "Authorization": "Bearer <databricks-token>",
    "Content-Type": "application/json",
  },
  json={
    "query_text": query_text,
    "query_vector": query_vector,
    "filters_json": json.dumps({"generator_serial": equipment_serial_number}),
    "num_results": k,
    "query_type": query_type,
    "columns": ["chunk_id", "pdf_name", "page_number", "chunk_text", "generator_serial"],
  },
  timeout=60,
)
response.raise_for_status()
results = response.json()
```

### Output Rules

- All columns from all four tables are included in each result record, grouped by source table.
- The grouped source objects are stable: each result contains `chunk`, `fsr_report`, `pdf_ref`, and `scraped_mapping` keys even when a join does not resolve.
- When metadata is missing for a returned chunk, the unmatched grouped object should be empty (`{}`) rather than omitted.
- Embedding-bearing columns such as `embedding` and `chunk_embedding` are excluded from the response payload even when they exist in the chunk table.
- Blank / null cells → `null`.
- Literal `"n/a"` → keep as string.

## Current Experiment vs Production Spec

1. **Service shape:** the current repository contains Databricks notebooks (`run_pipeline.py`, `run_evaluation.py`) and helper modules, not a deployed `query_fsr` REST service.
2. **Retrieval path:** this spec assumes one production path (`generator_serial` filter → internal Azure OpenAI query embedding → HYBRID retrieval with supplied `query_vector` → reranking → enrichment). The current experiment evaluates four modes instead: ANN/HYBRID with reranking on/off.
3. **Enrichment scope:** this spec expects runtime joins to three supplementary views and grouped response objects. The current experiment only enriches the chunk table with `generator_serial` and `report_date` from `vgpd.fsr_std_views.fsr_pdf_ref`; it does not construct joined `fsr_report`, `pdf_ref`, and `scraped_mapping` response payloads.
4. **Metadata assembly:** the standalone `query_fsr_with_metadata.py` sample now demonstrates the grouped response assembly path end to end: first-pass Vector Search retrieval, full chunk-row hydration by `chunk_id`, filename-normalized joins to the three metadata views, and grouped JSON output.
5. **Object names and embedding config:** the production catalog/schema names in this spec are target-state values. The current runtime defaults to `main.gp_services_sdg_poc.field_service_report` and self-managed Vector Search index `main.gp_services_sdg_poc.vs_field_service_report_gt_litellm`, with query embeddings produced via the configured LiteLLM/Azure OpenAI deployment.
6. **`page_number` semantics:** in the current pipeline `page_number` stores the chunk start page, and evaluation treats a hit as a cited page falling within `[page_number, page_number + PAGE_WINDOW]`. It is not a chunk ordinal.
7. **No-result behavior:** the standalone sample currently returns `200` with `results: []` plus diagnostic metadata such as `query_type`, `vs_index`, `chunk_table`, and `total_chunks_for_esn`. Production may still choose the stricter `404` contract documented below.
8. **Service operations:** request validation, HTTP status codes, authenticated caller logging, latency metrics, and publication to Confluence are defined here as production requirements, but they are not implemented in the cleaned notebook package.

## Recent Implementation Learnings

- `query_fsr_with_metadata.py` confirmed that the extra metadata fields are not returned by Vector Search directly; they are assembled only after a second-stage SQL lookup.
- The most robust implementation pattern is: minimal Vector Search return columns -> chunk hydration by `chunk_id` -> metadata joins by normalized PDF key and `(esn, event_id)`.
- Joins against `fsr_pdf_ref` need filename normalization and an ESN-aware selection rule to avoid attaching the wrong report metadata when multiple rows share a PDF stem.
- `_psot` deduplication needs a deterministic tie-break beyond status priority; the implementation now also falls back to latest end/start date and then report name.
- The grouped response should omit embedding arrays and keep empty metadata groups as `{}` for schema stability.
