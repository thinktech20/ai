## Issue 1: Missing `primary_esn` at Generator Subsection

### Symptom (as reported)
Region under `GAS TURBINE (297651 | SY0070884) > 3 Turbine > 3.1.1 Generator` had:
- No `primary_esn`
- `esn_source: "none"`, `esn_confidence: "none"`
- Fallback chain exhausted: `[local, parent, single_type, ibat_train, none]`

### Root Cause
**The issue was only in the standalone validation notebook, not in the pipeline.**

The standalone notebook (`run-preprocessor-standalone.ipynb`) called:
```python
result = preprocessor.preprocess(ctx)
```
No `ibat_resolver` was passed, so IBAT was never invoked despite appearing in the fallback chain.

The pipeline (`metadata_processor_v2.py`) correctly calls:
```python
_preprocessor.preprocess(ctx, ibat_resolver=ibat_resolver)
```
with a live IBAT resolver backed by `vgpd.prm_std_views.ibat_equipment_mst`.

### Verification
- IBAT table confirmed to have the expected entry:
  ```sql
  SELECT UPPER(TRIM(equip_serial_number)), UPPER(TRIM(equipment_type))
  FROM vgpd.prm_std_views.ibat_equipment_mst
  WHERE UPPER(TRIM(equipment_type)) = 'GENERATOR'
    AND UPPER(TRIM(equip_serial_number)) = '337X765'
  -- returns: 337X765 | GENERATOR
  ```
- Pipeline output (`fsr_metadata_v2.preprocessor_regions` for this document) shows:
  `primary_esn: "337X765"`, `esn_source: "ibat_train"` — correctly resolved.

### Fix Applied
The standalone notebook preprocessing cell now wires the production IBAT resolver:
```python
from fsr_v2.metadata_processor_v2 import _make_ibat_resolver
ibat_resolver = _make_ibat_resolver(spark, IBAT_TABLE)
result = preprocessor.preprocess(ctx, ibat_resolver=ibat_resolver)
```
Falls back gracefully to `None` outside Databricks.

The large char offset range (21885–55129) includes multiple sibling subsections, all correctly under the same parent.

- `primary_equip_type: "Gas Turbine"` — correct, this is sub-scope of GT work
- `section_path` includes `3.8\nPosition` — OCR artifact from page join, not a heading error

No fix required for Issue 2.

## Document fcb1511e-596a-4a56-b151-1e596afa569c: Section 3.8.7 Rotor Missing

### Symptom (as reported by Xujin)
Section `3.8.7 Rotor` is missing from the preprocessor output. Xujin asked whether it flipped back to Turbine (ESN 337X581).

**Correction from Xujin:** `3.8.7 Rotor` should be **Turbine** (Gas Turbine / 298464), not Generator. The assumption in the original RCA that it should be Generator was wrong.

### Evidence

TOC screenshot confirms the structure:
```
3.8.4 Hot Gas Path    p. 172
3.8.5 Exhaust and Bearing 2 Area  p. 174
3.8.6 Generator       p. 177
3.8.7 Rotor           p. 184
```

`3.8.7 Rotor` is a sibling of `3.8.6 Generator` under the same Gas Turbine parent (`3 Turbine > 3.4 Turbine`). It is the Gas Turbine rotor, not the Generator rotor.

**Expected behaviour after `3.8.6 Generator`:**
- The region for `3.8.6 Generator` should carry `primary_equip_type: Generator / 337X581`.
- `3.8.7 Rotor` should flip back to `Gas Turbine / 298464` (same as all other `3.8.x` siblings that are not Generator).
- The preprocessor detects `3.8.6 Generator` correctly, but after it ends the next detected region is `3.9.6 Inlet` — `3.8.7 Rotor` is completely absent.

From the preprocessor output:
- Region for `### 3.8.6 Generator`: present, `primary_esn: 337X581`, `primary_equip_type: Generator` — correct.
- Next region: `### 3.9.6 Inlet`, `primary_esn: 298464`, `primary_equip_type: Gas Turbine` — skipped over `3.8.7 Rotor`.
- There is no region for `3.8.7 Rotor` anywhere in the output.

### Root Cause (Confirmed)

**There were two cascading root causes:**

**Root cause 1: TOC contamination of SECTION_HDR context**

The SECTION_HDR loop (both the main `full_text` scan and the page-aware fallback) had no `toc_cutoff` guard. This allowed the TOC entry `4 Generator` at offset 2431 (well inside the TOC area, toc_cutoff = 12485) to be registered as an active SECTION_HDR candidate with `equipment_type = Generator`.

This polluted `context_type` for all sections after offset 2431, including `3.8.7 Rotor` at 60359. The result: SUBSEC_GENERIC promotion assigned Generator context to `3.8.7 Rotor` instead of Gas Turbine.

**Root cause 2: `SUBSEC_TURBINE` pattern did not cover `Rotor`**

After fixing the TOC contamination, `context_type` at offset 60359 became `None` (no relevant typed HEADER or SECTION_HDR in the body before that point). The SUBSEC_GENERIC guardrail skips candidates when `context_type is None`, so `3.8.7 Rotor` was dropped entirely.

The pattern `SUBSEC_TURBINE` matched `x.y Turbine` but not `x.y Rotor`. Since `Rotor` is a known Gas Turbine component, it should be included.

**Fix applied in commit `39e1b6d` (partially reverted — see Reopened below):**
1. Added `toc_cutoff` guard to SECTION_HDR main loop and page-aware fallback loop — prevents TOC section headings from polluting body context. **Keep.**
2. Added `Rotor` to `SUBSEC_TURBINE` pattern → `3.8.7 Rotor` is now detected as a typed SUBSEC with `equipment_type=None`. **Revert.**
3. Added flip-back logic to `_infer_equipment_for_untyped_subsections` — Rotor-titled spans skip the nearest-sibling lookup and inherit from the Gas Turbine parent (`3.2 Compressor`), resolving to `Gas Turbine / 298464`. **Revert.**

### Reopened — Xujin pushback on commit `39e1b6d`

Xujin flagged two problems with fixes (2) and (3):

- **Rotor is not always Turbine.** `Rotor` can belong to a Turbine section or a Generator section depending on the document. Hard-coding `Rotor` into `SUBSEC_TURBINE` and flipping it back to Gas Turbine breaks any document where `x.y Rotor` sits under a Generator parent.
- **The real bug is upstream.** The `3 Turbine` SECTION_HDR is stored with `equipment_type=None` because this document has no `GAS TURBINE (298464 | SY…)` HEADER line for the backward-scan to latch onto. If `3 Turbine` were correctly typed as `Gas Turbine`, then when SUBSEC_GENERIC evaluates `3.8.7 Rotor` the nearest typed SECTION_HDR context would be `3 Turbine → Gas Turbine`, `context_type` would be `Gas Turbine` (not `Generator`), the Generator guardrail would not fire, and Rotor would be promoted with the correct equipment type. Under a Generator parent the same logic would correctly give it `Generator`.
- **Additional suggestion (deferred):** cross-check detected section headers against TOC entries. Headers that appear in the TOC are real; “detected” headers with no TOC match (e.g. `3.8\nPosition` in b775cf29) can be filtered out. This is a broader enhancement, not required to fix this specific issue.

### 8-11 vs 8-12 evidence chain (confirms Xujin's diagnosis)

Diff of `preprocessor_code_0811_2.py` vs `preprocessor_code_0812.py` shows three interacting changes on 8-12 that together produced the regression:

1. **Bare `TURBINE` SECTION_HDR now types as `None` (was Gas Turbine).**

   8-11 (`_collect_heading_candidates`, SECTION_HDR loop):
   ```python
   equip_type = _canon(match.group(2))                       # bare "TURBINE" → "Gas Turbine" via _canon fallthrough
   section_root_type[num.split('.')[0]] = equip_type
   ```
   `_canon` returns `"Gas Turbine"` as its last-resort default, so `3 Turbine` was typed as Gas Turbine.

   8-12 (same block):
   ```python
   equipment_label = match.group(2)
   equip_type = None if equipment_label.upper() == "TURBINE" else _canon(equipment_label)
   if equip_type:
       section_root_type[num.split('.')[0]] = equip_type    # skipped when equip_type is None
   ```
   Now bare `TURBINE` explicitly becomes `None` — the exact upstream regression Xujin described.

2. **`SUBSEC_GT` was split — "Turbine" moved to a new `SUBSEC_TURBINE` that also types as `None`.**

   8-11:
   ```python
   SUBSEC_GT = r'...(?:Turbine|Compressor|Combustion|Inlet)\b'   # Turbine typed as Gas Turbine
   ```

   8-12:
   ```python
   SUBSEC_TURBINE = r'...(?:...) Turbine\b'                       # typed as None
   SUBSEC_GT      = r'...(?:Compressor|Combustion|Inlet)\b'       # Turbine removed
   ```

3. **A doc-inventory backfill was added, but in the wrong place.**

   8-12 added this inside `_resolve_span_esn_local_first` (which runs *after* candidate collection):
   ```python
   for span in spans:
       if span.equipment_type or not _is_bare_turbine_heading(span.heading_text):
           continue
       parent = spans[span.parent_idx] if span.parent_idx is not None else None
       if parent and parent.equipment_type in ("Gas Turbine", "Steam Turbine"):
           span.equipment_type = parent.equipment_type
           continue
       available_turbine_types = [t for t in ("Gas Turbine", "Steam Turbine") if active_by_type.get(t)]
       if len(available_turbine_types) == 1:
           span.equipment_type = available_turbine_types[0]
   ```

   The intent matches ours (disambiguate bare Turbine from doc-level inventory), but this back-fills the *span* — after `_collect_heading_candidates` has already evaluated SUBSEC_GENERIC. Inside SUBSEC_GENERIC, `context_type` is computed from the raw candidates list:
   ```python
   context_candidates = [
       c for c in candidates
       if c.start_char < match.start()
       and c.heading_type in (HeadingType.HEADER, HeadingType.SECTION_HDR)
       and c.equipment_type                          # filters out untyped 3 Turbine
   ]
   ```
   With `3 Turbine` still `None` at that point, it is filtered out. `context_type` at `3.8.7 Rotor` becomes `None` (or `Generator` from TOC contamination before the `toc_cutoff` fix), the `if not context_type: continue` guardrail fires, and `3.8.7 Rotor` is never emitted as a candidate. The later span-level backfill types `3 Turbine`, but by then Rotor is already dropped.

Sequence match to Xujin's message:

> "we assigned all Turbine to Gas Turbine, right? … later on … when we detect '3 Turbine' we assigned to None first. … 3 Turbine itself inherent from parent and got Gas turbine equipment tag, but that span's equip type was still none [at the time SUBSEC_GENERIC ran]. So later on when 3.8.7 wants to refer to parents, it go backs to 4 generator from ToC"

Every step in Xujin's message maps to a specific line in the 8-11→8-12 diff. Our fix in commit `c6fbd30` addresses exactly that gap by moving the doc-inventory fallback into `_collect_heading_candidates` at the SECTION_HDR loop, so `3 Turbine` is typed *before* SUBSEC_GENERIC evaluates `3.8.7 Rotor`.

### Revised fix (applied — commit `c6fbd30`)

1. **Kept** the `toc_cutoff` guard on both SECTION_HDR loops (unrelated to Rotor, valid fix).
2. **Reverted** `Rotor` from `SUBSEC_TURBINE` — pattern restored to match `x.y Turbine` only.
3. **Reverted** the Rotor flip-back branch in `_infer_equipment_for_untyped_subsections`.
4. **Added:** when a bare `Turbine` SECTION_HDR has `equip_type=None` and the backward-scan finds no prior Gas/Steam Turbine candidate, fall back to the document-level equipment inventory (title-page ESN discovery). If the document contains only Gas Turbine equipment, type the bare `Turbine` SECTION_HDR as `Gas Turbine` (mirror rule for Steam-only; ambiguous inventory leaves it `None`).
5. **Tests:** added `test_bare_turbine_section_hdr_typed_from_doc_inventory_when_no_header` reproducing the fcb1511e scenario.

**Verified output after revised fix:**
- `3 Turbine` SECTION_HDR: `equipment_type = Gas Turbine` (from doc-level inventory).
- `3.8.6 Generator`: `Generator / 337X581` ✓
- `3.8.7 Rotor` → SUBSEC_GENERIC path → `context_type = Gas Turbine` (nearest typed SECTION_HDR) → promoted as SUBSEC with `Gas Turbine / 298464` ✓
- Bonus: `3.9.x` subsections (`Reassembly`, `Bearing 1/2`, `Thrust Bearing`, `New GT Rotor`, `IGV Arm/Actuator`) now emit as distinct Gas Turbine regions (previously absorbed into an oversized region).

### Impact
The Generator region for `3.8.7 Rotor` pages extends beyond `3.8.6 Generator`. Content that belongs to the Gas Turbine rotor inspection is attributed to Generator (337X581) instead of Gas Turbine (298464).

### Fix
See Revised fix above — applied in `preprocessor_v2.py` (commit `c6fbd30`).

## Document fcb1511e-596a-4a56-b151-1e596afa569c: Chunk Contains Two Subsections / Wrong Equipment Attribution

### Symptom (as reported by Xujin)
- Chunk `9c910a17b1a1c5e6d39d461c574475c7` contains two subsections and is not split between them.
- In the July 31 version, sections `3.8.6 Generator` and `3.8.7 Rotor` were separate chunks. In the current version they are merged.

### Evidence

**Current chunk query result** (chunk index 23, page 139):
- `region_primary_esn: 298464`, `region_primary_equip_type: Gas Turbine`
- Chunk text contains `### 3.7.1 Unit Rotor` repeated ~20 times along with photo IDs (`DSC07346`, `DSC07347`, …)
- These are OCR page headers — each photo gallery page re-prints the current section heading, so the parser sees `3.7.1 Unit Rotor` as a repeated heading instead of a single boundary.

**July 31 chunks screenshot:**
- Rows 6291–6298 (pages 183–190): `region_primary_esn: 337X581`, `region_primary_equip_type: Generator` — correct (this is the `3.8.6 Generator` area).
- Rows 6299–6309 (pages 191–210, highlighted orange): `region_primary_esn: 337X581`, `region_primary_equip_type: Gas Turbine` — wrong equip_type for what should be `3.8.7 Rotor` (also Generator work).

### Root Cause

There are two distinct problems cascading from the same underlying cause.

**Root cause:** `3.8.7 Rotor` is a Gas Turbine section that should flip back from Generator after `3.8.6 Generator` ends, but it is not detected as a heading. Because no region boundary exists at `3.8.7`, the Generator region extends into Rotor content.

**Correction from Xujin:** `3.8.7 Rotor` should be **Turbine** (Gas Turbine / 298464). The original assumption that Rotor sections belong to Generator was wrong.

#### Problem A: Missing flip-back — 3.8.6 Generator region extends into 3.8.7 Rotor pages

In the current preprocessor version `3.8.7 Rotor` is missing entirely (see Issue 2 above), so its content is absorbed into the preceding `3.8.6 Generator` region. The Generator region now spans both the Generator pages and the Rotor pages, incorrectly attributing Turbine-rotor inspection content to Generator (337X581).

In the July 31 version, the orange-highlighted rows showed `region_primary_esn: 337X581` but `region_primary_equip_type: Gas Turbine` for pages 191+. This suggests that in July 31, `3.8.7 Rotor` was detected as a heading but was **correctly** attributed to Gas Turbine while still inheriting the Generator ESN from the IBAT lookup — a mismatch that was itself a separate issue. In the current version the heading is absent entirely.

#### Problem B: Repeated OCR heading in photo gallery pages

The chunk for `3.7.1 Unit Rotor` contains the heading `### 3.7.1 Unit Rotor` repeated ~20 times. This is because the PDF photo gallery pages each re-print the active section heading as a page header. The text extraction picks this up as many heading occurrences. The chunker does not split on repeated headings within a single region — it only splits at region boundaries — so all photo pages land in one chunk.

#### Connection to Issue 2

The chunk merge of `3.8.6` and `3.8.7` is a **direct downstream effect** of Issue 2 (missing `3.8.7 Rotor` heading). When the preprocessor does not detect `3.8.7` as a heading, no region boundary is created there. The chunker can only split at region boundaries, so it cannot separate `3.8.6 Generator` content from `3.8.7 Rotor` content — they form one large region and the chunker packs them into the same chunk(s).

### Impact
- Rotor inspection data is either misattributed to Gas Turbine or merged into the Generator region with no boundary.
- In retrieval, a query filtering by `region_primary_equip_type = Generator` may miss the Rotor chunks attributed to Gas Turbine, and vice versa.
- The repeated OCR page headers inflate chunk text with noise tokens, degrading embedding quality for those chunks.

### Recommended Fix
1. Fixing Issue 2 (detecting `3.8.7 Rotor` as a heading with flip-back to Gas Turbine) will automatically re-create the region boundary and allow the chunker to split the two sections again. No change is needed to the Generator keyword list — Rotor should remain Turbine/Gas Turbine.
2. Investigate whether photo gallery pages can be excluded from repeated heading extraction, or de-duplicated before region building, to reduce noise in chunk text.
